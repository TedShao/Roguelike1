# Roguelike1 方向讨论稿 v0.4

状态：用户已选择 A「逐回合连锁地牢」作为主方向，具体规则尚未确定，未开始开发。更新于 2026-10-23。

## 已确认与仍然开放的事项

- 本阶段只研究、机制拆解及讨论；不写游戏代码、不做原型。
- **最新平台优先级：Steam／桌面版优先，网页试玩可选。**
- **最新范围调整：不再限定 Three.js 或等距微缩画风，Godot 纳入候选。**镜头、2D／3D、主题与表现形式一起评估，暗黑童话保留为候选而非前置限制。
- **用户已选择 A「单角色逐回合连锁地牢」，采用“一步一响应”“关键预告”与“局内自由构筑”。**行动消耗、敌方响应细节及技能／符文／装备的具体规则尚未定案。“好玩、愿意再开一局”仍是目标；在线时间和奖励频率不单独代表趣味。
- **构筑重心已确定为少数技能相互配合，同时允许某个技能成为核心；技能以回合冷却为主要约束。**技能、符文与装备联动是重点探索方向，不等于三层系统都必须保留。
- 文档现纳入 [Roguelike1](https://github.com/TedShao/Roguelike1) 的 Git 管理；游戏开发与原型仍未开始。

## 想先解决的产品问题

玩家应能说出：**“我把原本能用的能力改造成了一种自己的打法，并且用它解决了这一局遇到的问题。”**这是研究后提出的体验假设，不是已经被验证的产品承诺。

它包含两个不同的乐趣来源：一是组合终于起效，二是起效后仍有值得做的决定。十款样本对这两者的支持和冲突见[比较报告](comparison.md)。不应在此时直接用“杀戮尖塔＋Hades＋Noita”定义产品：每加一个来源，都可能同时继承其制作成本和学习负担。

## 已选 A；保留三个方向的比较依据

以下具体数量与时长只是帮助讨论的例子，不是关卡规格或排期。候选 C 是战斗交互方式的变化，与 A 同属非实时决策的大类，但玩家控制粒度明显不同。

|方向|玩家亲自控制什么|最有辨识度的一刻|主要风险|可能更合适的表现|
|---|---|---|---|---|
|A 逐回合连锁地牢|每步位置、目标、技能与顺序|一次准确的推拉或施法，使整个房间发生预期连锁|算得太久、重复走格、最优解固定|俯视 2D、斜俯视 3D、可读的小型棋盘|
|B 轻动作构筑闯关|持续走位，少量主动施法；基础攻击可自动|自己把敌人聚到一起，亲手释放成型组合|躲避抢走欣赏构筑的注意力，动作制作成本高|轮廓清楚的 2D 或 3D 小战场|
|C 编排后爆发|战前技能关系、目标优先级与有限战中干预|按下执行，自己编排的能力链依次解决敌群|变成看演出，战斗没有局面性，一套配置通吃|桌面剧场、图示清楚的 2D、少遮挡的 3D|

### A：逐回合连锁地牢

**一段设想。**敌人预告关键危险攻击，普通行为通过观察学习。玩家可以先把一个敌人推入潮湿区域，再用电击触发范围传导；也可以放弃连锁，直接解除眼前威胁。两种做法都能理解，各有资源与位置代价。奖励让推击附带标记，或让电击留下持续区域，逐步改变原有能力，而不是只加伤害。

**循环。**观察房间 → 逐步行动和应对 → 获得奖励并调整能力 → 选择下一条风险路线 → 首领检验构筑 → 结束与新选择。探索可使用短路径或房间节点，避免清空房间后仍逐格空走。

**依据与代价。**杀戮尖塔支持从容决策与过渡取舍；最后的咒语提供回合内清场的专项参照。但它们不能证明地牢移动一定值得加入。A 需要位置真正改变结果，否则地图只是让玩家多点几次。

**差异化机会。**构筑直接改变空间规则：传播、推拉、穿透、区域和触发目标。玩家看到的应是战场变化，不是只在角色面板上增长。

**关键未知。**在没有实时动作时，单角色、少技能是否足够支撑多次重开？会不会每回合都要求长时间推演？弱构筑有没有靠位置挽救的空间？

**未来验证门槛。**同一遭遇中应能解释至少两种不同用途的行动；不要把选择数量当作好玩的证据。若多数回合只有一个显然正确答案，先改遭遇与技能关系，不继续增加道具。

### B：轻动作构筑闯关

**一段设想。**基础攻击自动处理最近威胁，玩家通过移动聚怪，再选择一个时机施放主动技能。房间结束后从容改造能力。新的符文改变攻击方向或触发条件，让下一场的走位也随之变化。

**循环。**选择路线 → 短战斗 → 立即展示收益 → 购物／改造 → 下一场压力变化。战斗和配置有清楚边界。可以用约半分钟到一分钟的房间作为讨论起点，但实际节奏必须验证，不能借土豆兄弟的数字直接定规格。

**依据与代价。**土豆兄弟说明自动攻击与间歇构筑可以共存；魔法工艺的评价提醒躲避和欣赏法术会争夺注意力。B 的风险在于删掉复杂操作后，剩下的移动也没有意义。

**差异化机会。**构筑改变玩家如何移动和选择释放时机；例如绕行积累能量、固定位置蓄力、诱导敌人进入路径，不只是自动输出更高。

**关键未知。**玩家是想亲手触发爆发，还是只想看构筑效果？首领是否会迫使所有流派都练习同一种闪避？成型后还能通过操作表达什么？

**未来验证门槛。**观察开启或取消某项主动输入后，玩家是否仍感到自己在做有意义的决定。若全部乐趣来自商店，而战斗只是等待，应重新考虑 C，而不是增加更多敌人。

### C：编排后爆发

**一段设想。**进入房间后看见敌人分布与部分意图。玩家把一组有限技能按触发关系连接，指定优先目标，按下执行。系统用短而可读的过程结算；剩余威胁促成下一次调整。玩家可保留一次应急干预，但不能随时改写所有规则。

**循环。**观察遭遇 → 调整编排 → 集中结算 → 根据结果重新决定 → 奖励改造。它不同于 A 的逐步走位，也不同于 B 的连续控制。不能把本局全部决定都提前挪到商店。

**依据与代价。**Balatro 支持非实时组合及结算的表现空间，背包乱斗提供关系可视化参照；将其迁移到地牢是新假设，并非已经被这两款验证。自动执行会减少动作负担，也会削弱临场掌控感。

**差异化机会。**“技能构筑”本身成为玩家可操作的对象：顺序、连接、资源流和目标都能看见。可以用少量组件制造不同程序，而非依赖数百种独立道具。

**关键未知。**编排是否会像写公式？玩家是否愿意因新敌人调整旧组合？一次执行过长时能否保持理解和参与？

**未来验证门槛。**新遭遇应促成有意义的局部调整；如果配置从第一关到首领都不变，就没有真正的临场构筑。执行过程中应能追溯关键结果，且允许加速已理解的重复表现。

## 三者可以共享的设计起点

这些是候选原则，而非已经敲定的规则：

1. 开局就提供能解决问题的能力；奖励逐步改变打法。
2. 每项奖励应能回答“现在补什么、以后可能变什么”；允许跳过或转化无用奖励。
3. 纠偏机会有限而可理解，避免无限刷到固定答案。
4. 构筑至少有一条看得懂的因果链；伤害明细按需展开。
5. 给成型构筑展示机会，也给玩家结束本局或接受新挑战的选择。
6. 局外优先提供可立即使用的新方向；是否加入永久数值，需单独讨论。

**讨论顺序建议：**先选玩家希望亲手控制的那一刻，再讨论单局节奏和失败代价，随后确定奖励与局外系统，最后匹配画风、镜头和引擎。不要同时投票十几个细节。

## 画风与镜头现在如何比较

以下为制作判断，尚未生成概念图或资产；“2D 一定便宜”“低多边形一定轻量”都不成立，成本取决于方向数、动画量、特效与变体。

|候选|视觉语言与细节|与玩法的关系|需要承担的成本|
|---|---|---|---|
|暗黑童话微缩 3D|夸张比例、陶土或木偶质感、少量暖光、低细节背景；危险用轮廓与地面纹样表达|A 的空间连锁易形成桌面棋局感，C 可像机关剧场；B 也可用但更怕遮挡|模型、绑定、动画、遮挡处理；暗场中保持目标可读|
|手绘或版画式俯视 2D|粗轮廓、有限色板、纸张与墨迹质感；技能用不同形状和运动轨迹区分|A 容易看清格局，B 便于控制战斗轮廓，C 便于表达关系|大量角色方向与动作可能昂贵；场景和特效不能压住单位|
|图形化炼金／机关桌面|卡片、符号、器皿与少量角色演出；关系线、端口、次序成为主要视觉|C 的构筑关系最直接，A 可做符号化地牢|减少探索临场感；必须避免界面像工具面板、角色缺乏情感|
|风格化 3D 俯视战场|强剪影、平整可读地面、较少墙体、方向明确的技能|B 更适合移动与聚怪；也可服务 A|动作与命中特效需打磨；镜头跟随与密集场面需验证|

无论选哪一种，地面危险、敌人意图、玩家位置和触发来源都必须有独立的视觉层级。装饰细节集中在休息和奖励区域，战斗中心保持清楚。允许减少闪烁、震动和重复演出；这些不是降低趣味，而是让规则仍然可读。

镜头不再预设固定等距。A 可比较正俯视与固定斜俯视；B 可比较固定房间与缓慢跟随；C 可优先保证关系和目标同时可见。是否允许旋转应由遮挡问题决定，不为展示模型而增加操作。

## 引擎判断：桌面优先使 Godot 更值得先评估

**来源事实：**Godot 提供 2D／3D 场景、动画、音频与界面相关编辑工具；Three.js 官方将其定位为 3D 库，游戏系统需要由项目组织。这是工具职责差异，不是游戏质量高低的结论。[Godot 编辑器说明](https://docs.godotengine.org/en/stable/getting_started/introduction/first_look_at_the_editor.html)、[Three.js 官方游戏教程](https://threejs.org/manual/pages/game.html)

|选择|对本项目的优势【制作推断】|主要代价／条件【制作推断】|当前处理|
|---|---|---|---|
|Godot|桌面优先；可在同一工具内组织 2D／3D、关卡、动画和界面；便于围绕游戏内容迭代|需要熟悉其场景和资源流程；插件、资产导入和目标设备表现仍需验证|**优先评估候选，尚未锁定**|
|Three.js＋网页技术|若网页分发、页面式构筑界面或现有 Web 能力重要，可灵活结合|完整游戏工具、内容编辑、存档和桌面包装等要额外组织；网页优先优势目前权重下降|保留为网页试玩或特殊表达候选，不再作为硬条件|

**网页试玩的实际边界【F】：**当前 Godot 稳定文档列出 Web 导出使用 WebAssembly／WebGL 2.0 与 Compatibility 渲染；支持单线程导出；Godot 4 的 C# 项目目前不能直接导出 Web。浏览器存储、音频与渲染等限制仍要验证。因此若后来确定必须共用网页版，应在语言和表现选择前纳入约束，而不是桌面完成后默认一键等价导出。[Godot Web 导出说明，2026-10-23 读取](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)

这轮未安装引擎、创建工程或跑性能对比；没有依据宣称某引擎更快多少、能省几周。网页试玩可以是控制内容和效果的入口，不必与桌面完整版完全相同。
